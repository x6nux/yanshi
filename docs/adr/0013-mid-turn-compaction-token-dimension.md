# ADR-0013: mid-turn 压缩的 token 会计以「未压缩历史」为统一量纲

- 状态：Accepted
- 日期：2026-08-05
- 相关：ADR-0006（压缩两条路径）、E2/PROP1（台账）、W4

## Context

`CompactingModel` 夹在 ADK 与真实模型之间：ADK 每次迭代递交一份历史，
`maybeCompact` 决定是否压缩，压缩后的结果**只交给内层模型，不回写 ADK 的 state**。
下一次迭代 ADK 仍然递交它自己那份未压缩的历史。

这个设计是有意的（ADK 的 state 归 ADK 管，压缩是传输层的事），但它制造了一个
**极易踩错的量纲陷阱**：`CompactingModel` 里任何「上次压缩时有多大」的记账，唯一
可比较的对象是**输入侧的未压缩历史**，因为那才是它下次会再看到的东西。

W4 发现这个陷阱已经被踩中了。`lastCompactTokens` 存的是 `res.TokensAfter`
（压缩**后**的大小），而 `inCooldown` 拿它与当前**未压缩**的历史相减当作「增长量」。
两者不同量纲，差值恒定偏大，于是历史一字未改也能越过 cooldown 再压一次 ——
同一份上下文被连续压缩两遍，每遍烧一次模型调用。

会踩中不是因为写的人粗心。存「压缩后有多大」在任何**会回写 state** 的设计里都是
对的；错的是这里不回写。这条信息不在类型里，只在这份设计里。

## Decision

**mid-turn 压缩的所有 token 会计，一律以「ADK 递交的未压缩历史」为量纲。**

具体到当前实现：

- `lastCompactTokens` 存 `res.TokensBefore`，语义是「上次触发压缩时，未压缩历史有多大」
- `inCooldown` 的 `tokens - lastCompactTokens` 因此是**真实增长量**
- 三个门（threshold / hard-force / cooldown）全部对同一个未压缩历史求值

判据很短：**如果一个数会与「下一次 ADK 递交的历史」比较，它就必须是同一量纲的数。**

## Consequences

**不可违反的约束：**

- 任何新增的 mid-turn 记账字段，只要参与与输入历史的比较，就**必须**存未压缩量纲。
  存压缩后的量纲是一个静默失效 —— 不报错、不崩溃，只是门在错误的时刻开合。
- 这条约束**不适用于 pre-turn 路径**（`ctxcompact.MaybeCompact`）。那条路径的调用方
  持有并替换自己的历史，压缩结果就是下次的输入，两个量纲重合。
  混淆两条路径的量纲规则，与混淆量纲本身一样危险。

**已知代价：**

- 「压缩后有多大」这个数在 mid-turn 路径上**没有**记账位置。真需要它（例如做压缩
  效果统计）时，正确做法是新增一个字段并在名字里写明量纲，而不是复用现有字段。

**为什么要写下来：** 这条约束在类型系统里留不下痕迹 —— 两个数都是 `int`，存错一个
编译照过、测试照绿。W4 之前它已经错了一段时间，没有任何机制发现。
`internal/llm/eino::TestCompactingModel_CooldownDefersReCompact` 现在守着它，
但那条测试守的是**行为**；这份 ADR 守的是**下一个人的推理**。
