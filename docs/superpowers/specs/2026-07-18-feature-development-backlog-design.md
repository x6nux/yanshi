# 后续功能开发总表重构设计

## 目标

将 `docs/feature-comparison-with-codex.md` 重写为纯后续功能开发清单。文件不再承担全量功能盘点职责，不出现已经完成或只需保持的功能。

## 筛选规则

只保留当前状态为以下三类的能力：

- `部分`：主流程已有基础，但仍有明确交付缺口。
- `占位`：存在代码、类型或入口，但没有形成可用主流程。
- `缺失`：当前仓库没有可用实现。

删除所有 `已有` 和 `差异化` 条目，包括正文中的已实现能力总结、优势清单和仅需保持的能力。若某项差异化能力仍有增强空间，也不在本文件保留；增强工作应在独立维护计划中管理。

## 文件结构

文件只包含：

1. 标题、分析日期和筛选范围。
2. 三种状态的简短说明。
3. 一个后续功能开发总表。

删除原有规模对比、已实现能力摘要、分离的 P0-P3 backlog、里程碑说明、测试基线和代码证据索引，避免与总表重复或偏离“只看后续开发”的用途。

## 总表列

| 列 | 用途 |
| --- | --- |
| ID | 稳定功能编号 |
| 领域 | 功能所属模块 |
| 后续功能 | 需要建设或补齐的能力 |
| 状态 | 仅允许部分、占位、缺失 |
| 当前缺口 | 说明现有基础和未完成边界；缺失项直接说明没有实现 |
| Codex 参考 | `reference/codex` 中可借鉴的能力 |
| 开发目标 | autocode 应交付的目标，不要求机械复制 Codex |
| 优先级 | 仅允许 P0、P1、P2、P3 |
| 依赖 | 前置功能 ID；无依赖时写 `-` |
| 验收标准 | 可验证的最小完成条件 |

## 排序与依赖

- 先按优先级 P0 到 P3 排序，同优先级内按领域排序。
- 每项能力只出现一次，避免总表和 backlog 双重维护。
- 依赖必须引用同表中的 ID，不能引用已删除的已实现功能。
- 现有 ID 尽量保留；需要拆分或合并时以开发交付边界为准。

## 验证

- 总表只包含 `部分`、`占位`、`缺失`。
- 总表优先级只包含 P0-P3，并按优先级非递减排列。
- 每行列数一致，ID 唯一，所有依赖 ID 均存在。
- 全文件不出现已实现功能清单、优势清单或 `状态=已有/差异化` 的条目。
- 运行 `git diff --check`，确认 Markdown 无空白错误。
