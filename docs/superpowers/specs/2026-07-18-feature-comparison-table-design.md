# 功能对比文档单表重构设计

## 目标

将 `docs/feature-comparison-with-codex.md` 中第 3 节的 autocode 功能清单和第 4 节的 Codex 对比表合并为一个巨大主表，使读者能在同一行看到两边能力、完成度、差距和开发优先级。

## 表格结构

主表使用以下固定列：

| 列 | 内容 |
| --- | --- |
| 编号 | 稳定行号，格式为领域字母加两位序号 |
| 领域 | Agent 核心、工具、安全、CLI/TUI、会话与服务、任务/VCS、扩展生态、运维 |
| 功能 | 对比的最小独立能力 |
| autocode 状态 | 已有、部分、占位、缺失或差异化 |
| autocode 当前实现 | 已接入的实现、实际边界及必要代码证据 |
| reference/codex 能力 | 本地 Codex 快照中的对应能力 |
| 差距/建议 | 是否需要追平，以及推荐实现方向 |
| 优先级 | P0、P1、P2、P3、保持或不追平 |

## 内容组织

1. 删除原第 3 节的六个分散功能表。
2. 删除原第 4 节的重复逐域对比表。
3. 新建一个“完整功能对比总表”，按领域排序，而不是按优先级排序。
4. 每项能力只出现一次；相近但完成度不同的能力拆行，例如 MCP client 和 MCP server 分开。
5. 保留文档开头的状态说明、结论摘要，以及表后的 P0-P3 backlog、开发顺序、测试基线和代码证据索引。

## 一致性要求

- 不把目录、测试桩、未装配代码或设计文档标记为已完成功能。
- `autocode 状态` 必须与 `autocode 当前实现` 描述一致。
- 每个 P0-P3 建议都应能映射到后续 backlog；差异化能力标记为“保持”。
- Codex 的实验能力要在描述中注明，避免把实验代码误写成稳定产品能力。
- 合并后不保留重复表格，确保巨大主表是唯一的功能对比入口。

## 验证

- 检查 Markdown 表格每行列数一致。
- 搜索原第 3、4 节标题，确认已被单一总表替换。
- 运行 `git diff --check`，确认无空白错误。
- 抽查 MCP、插件、Goal token budget、sandbox 和测试基线等已知边界没有在重构中丢失。
