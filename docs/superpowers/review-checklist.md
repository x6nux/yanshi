# 评审清单（固定尺子）

**这份文件的作用：把评审技术锁死。**

## 为什么要锁

S0/W1 工作包连续多轮评审、每轮都开出阻塞，「连续三轮干净」的计数器一次都没超过 0。
复盘的结论不是代码在变差，而是**评审技术每轮在升级**：

- 前几轮：读计划文本，比对承诺与实现。
- 中间几轮：造探针，实测门禁会不会红。
- 最后一轮：首次系统性用**变异测试**（把被测函数掏空，看测试会不会红）—— 那一轮开出的阻塞里，多数只有这一种手法能发现。

于是「干净」成了移动靶：用上一轮的尺子量，修复是干净的；用下一轮的尺子量，不是。
**尺子不变了，「连续三轮干净」才是可达目标。**

## 怎么用

- 每一轮评审**跑完整份清单**（A–I），不挑不减。清单只能加，不能删。
- 本清单是**下限不是上限**：发现新手法，先把这一轮跑完，再把新手法补进清单，从下一轮开始生效。
- 清单里每条手法都**在本仓真实抓到过东西**，实例附在条目末尾。它们不是理论风险。
- 不写「要仔细」「要实测」这类无法执行的话。每条都是：**做什么 / 怎么做 / 什么输出算发现问题**。

---

## 0. 评审者纪律（先读这条）

评审者自己也会出错，而且出过。清单的第一条规则是约束评审者，不是约束被评审者。

**做什么**：每一条阻塞指控都必须可复现、可反驳。

**怎么做**：每条指控写成三段：

1. **可复现命令**（能原样粘进终端跑的那种）
2. **实际输出行**（贴真实输出，不是「大概会输出」）
3. **结论**（这行输出为什么构成问题）

**什么算不合格的指控**：

- 只有断言没有命令 —— 直接作废，不进阻塞列表。
- 命令是 `grep`，但没验证过 `grep` 的模式覆盖了所有写法 —— 窄 `grep` 造成的误报在本仓发生过。
- 计数类指控没有实际数一遍 —— 见下方实例。

**真实实例（评审者自己错的）**：

- 某轮评审报「有 10 个 GOOS 后缀测试文件」，实测是 8。原因：`_unix` 不是文件名层面的 GOOS 记号（`go tool dist list` 里没有 `unix`，它只能写进 `//go:build`），`..._windows_cov_test.go` 的末位元素是 `cov` 也不构成约束。**连清点这个洞的那次清点本身都数错了。**
- 另一轮的一条指控因 `grep` 模式太窄成了误报 —— 被指控的东西存在，只是写法不在模式覆盖范围内。

**被评审者有权反驳。** 附了命令和输出的指控可以被「你的命令漏了 X 写法」推翻；推翻后该条从阻塞列表移除，并记进本清单的手法改进。

## A. 变异测试（最高优先级）

这是最后一轮才首次系统性使用、并且一次性开出最多阻塞的手法。**它排在最前面。**

**做什么**：把被测函数掏空，跑它在台账（`docs/feature-status.yaml`）里声称的证据测试。

**怎么做**：

1. 从台账 evidence 里取出被引测试与它声称覆盖的函数。
2. 在被测函数体开头插入短路：
   - 有副作用的过程 → `if true { return }`
   - 有返回值的函数 → 直接 `return` 零值 / 空切片 / `nil`
   - 纯变换函数 → `return` 输入本身（恒等变换，比零值更隐蔽，也更接近真实退化）
3. 跑那条证据测试：`go test ./<pkg> -run '^<TestName>$' -v`
4. **恢复改动**（`git checkout -- <file>`），不要把掏空的代码留在工作树里。

**什么算发现问题**：

- **测试仍 PASS = 证据无效。** 这条证据不证明任何东西，台账条目是虚报。
- 测试 PASS 且输出里有 `--- SKIP`：属于同一问题的**更隐蔽形态**，见下方实例。
- 只有部分子测试红：说明证据覆盖面小于台账声称的子句范围，按部分虚报处理。

**真实实例**：`internal/ctxcompact.EnforceToolCallPairs` 掏空后，台账 `E2/PROP1#3` 引用的三条属性测试**全部 PASS**。原因：属性测试的前置条件守卫用**被测函数自己的产物**算 skip 条件，函数一掏空，每个 trial 都在守卫处 skip，而 `go test` 对 0 个执行 trial 报 PASS —— 与真正通过在退出码、在输出、在 CI 日志里都不可区分。

修复后的参考实现：`internal/ctxcompact/plan_property_test.go` 的 `runPairingProperty` / `minPairingTrials` —— 守卫（`skipAlreadyCompacted`）只读**生成的输入**、绝不读被测函数的输出，并且断言实际执行的 trial 数下限。这条约定**不是机器强制的**（理由见 ADR-0011 边界），只能靠本清单在评审时看。

**推论（写给被评审者）**：凡带前置条件守卫的属性测试，必须断言实际执行的 trial 数下限。

## B. 门禁探针（正反两向，缺一不可）

**做什么**：对每一道声称"会拦住 X"的门禁，实测它拦得住 X，且不误伤合法用法。

**怎么做**：

1. **正向探针**：在被扫描范围内造一个**应该被抓住**的违规，跑门禁，确认变红，读错误信息是否指向正确位置。
2. **反向探针**：造一个**形似违规但合法**的用法，跑门禁，确认不红。
3. 两个探针都跑完再删掉（`git checkout` / 删文件），确认工作树干净。

**只跑正向是半个探针。** 一道会误伤的门禁最终会被删掉，那比漏检是更大的洞 —— 所以反向探针不是可选项。

**什么算发现问题**：

- 正向探针全绿 → 门禁存在漏检，该门禁支撑的验收子句是虚的。
- 反向探针变红 → 门禁会误伤，它的寿命有限，等同于没有。
- 门禁红了但错误信息指不到具体文件/符号 → 按「可用性缺陷」记，不算阻塞但要记。

**真实实例**：`internal/archtest/removal_test.go` 的 `d2Mentions` 最初只有中文模式。本仓多份文档（README、`docs/vcs.md`、`docs/commit-convention.md`、若干 spec）是**英文正文**，一句英文的重新宣传可以全绿通过 —— 而 D2/O12 的第二条验收子句除这个测试外没有别的证据，**这条子句对最可能违反它的那批文档整体失效**。同时反向探针也必须过：`.vscode` 出现在忽略项列表里、`ide-vscode` 是提交 scope，两者都不是「这东西还在售」的声明，词级匹配会在两处误伤 —— 所以现在的模式刻意要求产品名与那几个词**相邻**。

## C. 测试名核对（这个陷阱在本项目骗过一次）

**做什么**：跑任何 `-run` 之前，先确认那个测试名真实存在。

**怎么做**：

```sh
grep -rn '^func Test' internal/<pkg>/ | grep <关键字>
```

确认名字逐字一致（大小写、下划线、子测试路径）后再跑 `go test -run`。

**什么算发现问题**：`go test -run <错名>` 匹配 0 个测试时**退出码是 0，输出行以 `ok` 开头**。任何只看退出码、只 `grep FAIL`、或只扫行首的检查都会把它读成通过。

具体分两种形态，**危险程度不同**（本条经实测校正，不要凭印象记）：

| 形态 | 实际输出 | 可见性 |
|---|---|---|
| 顶层测试名写错 | `ok  <pkg>  0.298s [no tests to run]` | 有标记 |
| 子测试路径写错（`-run 'TestX/nosuchsub'`） | `ok  <pkg>  0.229s [no tests to run]` | 有标记，但 `-v` 下同时出现一条真的 `--- PASS: TestX` |

`[no tests to run]` 标记**两种形态都会打**，`(cached)` 行上也保留 —— 所以它不是隐形的，只是容易被跳过。

真正的陷阱在第二行：`TestX` 匹配上了、父测试体**真的执行并 PASS**，只有子测试被过滤掉。`-v` 输出长这样：

```
=== RUN   TestReal
--- PASS: TestReal (0.00s)          ← 货真价实
testing: warning: no tests to run   ← 但断言一条没跑
ok  	tn	0.119s [no tests to run]
```

只盯 `--- PASS` 就会认定断言执行过了。多包 `go test ./...` 时更隐蔽 —— 标记只出现在不匹配的那一行，混在一堆 `ok` 里。

**判别方法**（对两种形态都有效）：加 `-v`，数实际执行的测试。

```sh
go test ./<pkg> -run '^<Name>$' -v 2>&1 | grep -c '^=== RUN'
```

结果为 0 = 零匹配。用子测试路径时改数 `--- PASS`/`--- FAIL` 的条数，并与预期的子测试数对账 —— 父测试的那条 PASS 要减掉。

更省事的办法：直接 `grep '[no tests to run]'`，两种形态一网打尽。

**这条陷阱同时污染 A 和 B。** 变异测试用错名跑，会看到 `ok` 并错误地判定「掏空后仍通过 = 证据无效」；门禁探针用错名跑，会看到 `ok` 并错误地判定「探针没被抓住 = 漏检」。**两个方向都会产生假阳性指控。** 所以 C 必须在 A、B 之前执行。

## D. 空壳测试识别

**做什么**：逐条读证据测试的断言，判断它有没有可能失败。

**怎么做**：对每条被引测试问四个问题，各有对应的搜索手法。

### D1. 恒真断言

对字面量或对自己刚构造的常量断言。

```sh
grep -rn 'assert\.\|require\.\|if .* != ' internal/<pkg>/<file>_test.go
```

**判据**：断言两侧是否都不依赖被测代码的输出。像 `4/2 >= 2` 这种，无论被测代码怎么变都是真。

### D2. 吞错

```sh
grep -rn 't\.Logf\|t\.Log(' internal/<pkg>/*_test.go
grep -rn '_ = ' internal/<pkg>/*_test.go
```

**判据**：`err != nil` 分支里只有 `t.Logf` 没有 `t.Error`/`t.Fatal`；或返回值被 `_ =` 丢弃后再没被检查。**`t.Logf` 吃掉错误 + `_ = out` 是本仓出现过的组合形态。**

### D3. fake 太宽

**判据**：fake 是否检查了**关键入参**？还是不看入参、硬编码返回正确值？

一个不看 argv 的 fake 进程会让「argv 表写错」这类 bug 完全不可见 —— 无论被测代码把 argv 拼成什么，fake 都返回成功。

**真实实例**：`internal/tools/diagnostics.go` 的探针 fake 最初不看 argv，硬编码返回成功，**盖住 bug 达三轮**。修复后的形态见 `internal/tools/diagnostics_test.go`：fake 现在断言 `spec.Args` 与期望表逐项相等，argv 不匹配时**模拟真实二进制的拒绝**（返回 `flag provided but not defined` 与非零退出），并由 `TestDiagnosticsProbesEachToolchainWithItsOwnVersionArgv` 把每个程序的 argv 逐条钉住。

**通用判据**：**fake 必须拒绝真实实现会拒绝的输入。** 一个只会成功的 fake 不是 fake，是常量。

### D4. spy 只证明调用发生

**判据**：spy 记录了「被调用了」，但**结构上看不见**调用的后果 —— 子进程的环境变量、退出码、资源是否回收、goroutine 是否退出。

一个返回 stub 的 spy 让所有这些都不可观测。判别方法：问「如果被测代码把环境变量传错/不回收子进程，这个 spy 会红吗？」答案是「不会」就是 D4。

**什么算发现问题**：以上任一命中，该测试不构成证据，台账里引用它的子句按虚报处理。

## E. 不会被执行的测试

**做什么**：确认每条证据测试在默认 `go test ./...` 下真的会编译并执行。

**怎么做**：逐项排查五种形态。

| 形态 | 检查命令 | 说明 |
|---|---|---|
| `testdata/` 下 | `find . -path '*/testdata/*' -name '*_test.go'` | Go 工具链完全忽略 `testdata/` |
| 文件名式 GOOS/GOARCH 约束 | `ls internal/<pkg>/*_test.go` 看后缀 | `foo_windows_test.go` 在 darwin 上**不编译**，且不需要任何 `//go:build` 注释就生效 |
| `//go:build` 约束 | `grep -rn '//go:build' internal/<pkg>/` | `e2e_real` 等标签下的测试默认不跑 |
| 无条件 `t.Skip` | `grep -rn 't\.Skip' internal/<pkg>/` | 函数体开头就 skip，`go test` 编译它、运行它、报它通过 |
| 条件 skip 导致 0 trial | 见 A 的实例 | skip 在子测试闭包里，条件由被测函数的产物算出 |

**权威判据**：`go test ./... -run '^TestZZNonexistent$' -v` 不会告诉你哪些编译了。用这个代替：

```sh
go test ./<pkg> -run '^<TestName>$' -v 2>&1 | grep -E '^(=== RUN|--- (PASS|FAIL|SKIP))'
```

没有 `=== RUN` 行 = 没跑（可能是零匹配，见 C；也可能是文件根本没编译）。有 `--- SKIP` = 跑了但没断言。

**什么算发现问题**：证据测试落在以上任一形态 → 它没有在默认 CI 路径上验证过任何东西。文件名式 GOOS 约束**尤其容易漏**：它不需要注释行就生效，而只扫 `//go:build` 的检查看不见它（本仓的 GOV8 曾因此文档比实现强了一档，见 ADR-0011）。

## F. 文档虚报扫描

本仓已抓到多处。**这类问题的共同点：写下的那一刻是对的，之后无声腐烂。**

**做什么**：对文档里每条**事实型断言**实际去数、去跑、去查。不要读着像对就放过。

**怎么做**：按五种形状分别扫。

### F1. 具体计数

**扫法**：`grep -rnE '[0-9]+ ?(处|条|个|项|files?|places?)' docs/ CLAUDE.md`

对每个数字实际数一遍。**数字在写下的那一刻就开始腐烂** —— 代码增删不会回来改文档。

**真实实例（均为历史发现）**：CLAUDE.md 里 `exec.Command*` 的处数写下时是对的，评审时实测已经不符；某处「5 条 partial」实测是 12。

**结论倾向**：文档里的精确计数应当**改成不带数字的描述**，或改成「由 `<某命令>` 打印」。保留计数就等于承诺每次改代码都回来改文档。

### F2. 描述另一个文件当前内容的句子

**扫法**：找形如「X 文件里写的是 Y」「台账文件头写 `""`」的句子，逐条打开那个文件核对。

**真实实例**：某处文档描述了台账文件头的当前措辞，而台账在**十几分钟后**就被改了 —— 这类句子的半衰期以分钟计。

**结论倾向**：改成引用（「见 `<路径>` 的文件头」），不复述内容。

### F3. 行号引用

**扫法**：`grep -rnE '\.go:[0-9]+' docs/ CLAUDE.md`

**判据**：行号在任何一次插入删除后失效，且失效**无声**。改用**符号引用**（函数名、类型名、常量名）—— 符号改名时 `grep` 找得回来，行号漂移找不回来。

### F4. 断言型陈述（最危险）

形如「X 是 Y」「边界是 Z」的架构断言，读起来权威，但从没有人实测过。

**扫法**：找文档里所有关于**安全边界、隔离、强制点、唯一入口**的陈述，逐条设计实验去证伪。

**真实实例**：某处曾断言隔离边界是 guard 层加网络策略 —— 实测**证伪**，随后有两次提交专门收回这类陈述（`c1500ae` 停止把某个已死端口的代理称作被强制的边界；`ca08d9f` 停止断言出口流量被阻断）。

**判据**：一条安全性断言如果**没有测试钉着它**，它就是一句愿望。要么补测试，要么把断言降级成「意图」并写明当前实际状态。

### F5. 幻影引用

见 H。

**什么算发现问题**：任一条事实型断言与实测不符 → 阻塞。**注意本清单自己也受 F 约束**：本文件刻意不写任何关于其他文件当前内容的计数。

## G. 接线激活的路径要当新代码审

**做什么**：找出本轮把「已写但没接进组合根」的代码接活的改动，把被接活的路径**当全新代码从头审**。

**怎么做**：

1. 找接线点：`internal/bootstrap` 里新增的 `Build*` 调用、新绑定的 context 注入器、新增的 factory 绑定。
2. 对每个被接活的分支，问：**这条路径以前从没在生产里跑过，回落路径才是一直在跑的那条。**
3. 重点查四类（都是子进程/资源类）：
   - **环境**：新路径是否传了 `PATH` / `HOME` / 工作目录？回落路径继承了进程环境，新路径可能从零构造。
   - **返回值**：新路径是否真的把退出码/错误传回去了？以前不可达的分支里可能有死代码。
   - **资源回收**：`Wait` / `Close` / `cancel` 在**每一条**退出路径上都调了吗？
   - **取消与超时路径**：成功路径修好了，不等于取消路径修好了。

**什么算发现问题**：被接活的路径上任一条与回落路径行为不一致，且没有测试覆盖该差异。

**真实实例**：`shell_run` 从直接 pipe 改走 `SecureProcessFactory` 后，一次接线暴露出三个从没跑过的缺陷 —— 子进程没有 `PATH`/`HOME`、退出码 footer 是死代码、**从不调 `Wait`**（每次 `shell_run` 漏一个未回收的子进程）。而且第一次修复只覆盖了成功路径：**流式错误路径**（也就是 TUI 按 Esc 取消、`timeout_s` 到期离开该函数的那条路）仍然直接 return，子进程和抽管道的 goroutine 一起永久驻留。唯一覆盖它的测试用的是 spy（见 D4），**结构上看不见这些**。当前形态见 `internal/tools/shell.go` 里 `reap` 闭包 + `defer reap()` 那段以及它上方的注释。

## H. 幻影名扫描

**做什么**：配置、文档、profile、注释里出现的每一个工具名、字段名、路径、环境变量名，`grep` 确认真实存在。

**怎么做**：

```sh
# 从 config.example.yaml / profiles / 文档里抽出所有名字，逐个：
grep -rn '"<name>"' internal/ --include='*.go'
# 零结果 = 幻影
```

对工具名，还要确认它**被注册**（不只是字符串存在于某处注释里）。本仓有 GOV5/GOV7 两道门禁做这件事，但它们只覆盖 orchestrator profile 与 guard 的免提示集 —— **文档里的名字不在门禁范围内**，必须靠本条手动扫。

**什么算发现问题**：

- 名字在配置/文档里出现但代码里不存在 → 幻影。**幻影让 profile 读起来比实际权限宽**（一个 allow 条目不对应任何真实工具），或让文档承诺一个不存在的能力。
- 名字存在但**没被注册** → 同样是幻影，只是藏得更深。

**真实实例**：

- `http_request` 是文档里的幻影工具名 —— 真实注册的是 `web_fetch` 与 `web_search`（`internal/tools/web.go` 里的注册调用）。**注意扫这个名字时会命中本文件这一行**：一份记录幻影名的文档本身就是该名字的一次出现，`grep` 的结果要减掉清单自己，否则会把「已清理」误读成「仍存在」。这正是 F2 说的那种自指陷阱。

## I. 竞态与资源

**做什么**：跑 race detector，并单独验证取消/超时路径。

**怎么做**：

```sh
go test -race ./internal/<改动的包>
```

- 真实 race 会**稳定复现**（连跑 3 次全挂）；时序 flake 通常重试即过。判别方法：`for i in 1 2 3; do go test -race ./internal/<pkg> || echo FAIL; done`。3/3 挂 = 真 race，不是 flake。
- 取消/超时路径**单独验证**，不要假设成功路径的修复覆盖了它：
  - 子进程被回收了吗？（`Wait` 被调用）
  - goroutine 退出了吗？（抽管道的那些最容易漏）
  - `context` 取消后有没有仍在写的 channel？

**什么算发现问题**：

- `-race` 稳定报警 → 阻塞。
- 取消路径上有 `return` 绕过了资源回收 → 阻塞，即使成功路径已经修好。**这正是 G 的实例里第二次才发现的那种。**

## 一轮评审的执行顺序

顺序有依赖，不要打乱：

1. **C（测试名核对）** —— 先做，否则 A、B 的结论全是假阳性。
2. **E（不会被执行的测试）** —— 排除掉根本没跑的测试，缩小 A 的范围。
3. **A（变异测试）** —— 对剩下的证据测试逐条掏空。
4. **D（空壳测试识别）** —— A 没抓到的，用读代码补。
5. **B（门禁探针，正反两向）** —— 对每道门禁。
6. **G（接线激活的路径）** —— 对本轮的接线改动。
7. **H（幻影名）+ F（文档虚报）** —— 全仓扫。
8. **I（竞态与资源）** —— 收尾。

跑完记得：`git status` 确认探针和掏空的改动都已恢复，工作树干净。

## 「干净」的定义

**一轮干净 = 完整跑完 A–I 九条，零阻塞。**

不是「没发现问题」，是「按这九条找过，没找到」。少跑一条就不算这一轮，不能计入「连续三轮」。
