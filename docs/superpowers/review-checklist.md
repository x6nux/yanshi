# 评审清单（固定尺子）

**这份文件的作用：把评审技术锁死。**

## 为什么要锁

S0/W1 工作包连续多轮评审、每轮都开出阻塞，「连续三轮干净」的计数器一次都没超过 0。
复盘的结论不是代码在变差，而是**评审技术每轮在升级**：

- 前几轮：读计划文本，比对承诺与实现。
- 中间几轮：造探针，实测门禁会不会红。
- 最后一轮：首次系统性用**变异测试**（把被测函数掏空，看测试会不会红）—— 那一轮开出的阻塞里，多数只有这一种手法能发现。

于是「干净」成了移动靶：用上一轮的尺子量，修复是干净的；用下一轮的尺子量，不是。
**尺子不变了，「连续三轮干净」才是可达目标。**

⚠️ **「尺子不变」的准确含义是「不静默地变」，不是「永不变」。** 第 22 轮加了 J、第 24 轮加了 K —— 两次加的都是**结构性**盲区，不是一次技术升级。区别在于两条纪律：新手法**从下一轮才生效**（「怎么用」第二条），且每次改动都记进文末的「本尺子的修订记录」。有了这两条，一次加条是**可核算的**判据变更，读者能算出任何一轮当时的判据是什么；没有它们，就退回成移动靶。

## 怎么用

- 每一轮评审**跑完整份清单**（A–K；生效轮次见「「干净」的定义」那张表），不挑不减。清单只能加，不能删。
- **`0-bis` 不是手法**，它约束的是写代码的人。它不计入 A–K，也不改「干净」的定义。
- 本清单是**下限不是上限**：发现新手法，先把这一轮跑完，再把新手法补进清单，从下一轮开始生效。
- **加条必须记进文末的「本尺子的修订记录」**，带轮次与理由。不记录的加条是一次静默的判据变更 —— 它让此前每一轮的「干净」失去意义，而这正是本清单要防的那件事。
- 清单里每条手法都**在本仓真实抓到过东西**，实例附在条目末尾。它们不是理论风险。
- 不写「要仔细」「要实测」这类无法执行的话。每条都是：**做什么 / 怎么做 / 什么输出算发现问题**。

## 0. 评审者纪律（先读这条）

评审者自己也会出错，而且出过。清单的第一条规则是约束评审者，不是约束被评审者。

**做什么**：每一条阻塞指控都必须可复现、可反驳。

**怎么做**：每条指控写成三段：

1. **可复现命令**（能原样粘进终端跑的那种）
2. **实际输出行**（贴真实输出，不是「大概会输出」）
3. **结论**（这行输出为什么构成问题）

**什么算不合格的指控**：

- 只有断言没有命令 —— 直接作废，不进阻塞列表。
- 命令是 `grep`，但没验证过 `grep` 的模式覆盖了所有写法 —— 窄 `grep` 造成的误报在本仓发生过。
- 计数类指控没有实际数一遍 —— 见下方实例。

**真实实例（评审者自己错的）**：

- 某轮评审报「有 10 个 GOOS 后缀测试文件」，那一轮实测是 8（历史快照，见 F 段末尾那张三档表）。原因：`_unix` 不是文件名层面的 GOOS 记号（`go tool dist list` 里没有 `unix`，它只能写进 `//go:build`），`..._windows_cov_test.go` 的末位元素是 `cov` 也不构成约束。**连清点这个洞的那次清点本身都数错了。**
- 另一轮的一条指控因 `grep` 模式太窄成了误报 —— 被指控的东西存在，只是写法不在模式覆盖范围内。

**被评审者有权反驳。** 附了命令和输出的指控可以被「你的命令漏了 X 写法」推翻；推翻后该条从阻塞列表移除，并记进本清单的手法改进。

## 0-bis. 实施纪律：注释里的机制断言必须被钉住

⚠️ **这一条约束的是写代码的人，不是评审的人。** 它**没有字母编号**，不进 A–K，也**不改「干净」的定义** —— 它是修复动作本身的验收条件，评审者只负责在 diff 里看它有没有被遵守。

**什么是「机制断言」**：任何形如「X 之所以是这样，是因为不这样会导致 Y」的句子。「这个组不能为空，否则 Z 会被匹配」「这两个维度的顺序不能换，否则会静默授权」「这个字段必须先判 nil，否则会读到零值」都是。它们看起来是解释，实际上是**未经检验的因果主张**，而且是最有说服力的那种 —— 读者不会去验证一句听起来这么具体的话。

**规则：写下它的人必须造一次变异** —— 把 X 改成「不这样」，跑测试，看 Y 是否真的发生。三种结局各有落地方式：

| 变异结果 | 该做什么 |
|---|---|
| **真的红** | 把触发它的用例写进表/测试，注释里**指向那个用例**（例如「把这个组改成可选，正是下面那两行变红」）。断言从此可被后来人一条命令复核。 |
| **不红** | 这条断言是假的，或者机制另有其人。**必须查明真正的机制**再写，不能凭直觉换个说法交差。查明后回到上一行。 |
| **确实钉不住**（纯风格取舍、可读性偏好） | 显式写成「未钉住的设计选择」，**不要伪装成有因果的机制**。一句诚实的「这里没有测试拦着」比一句听起来严密的假因果便宜得多。 |

**为什么这不是理论风险 —— 连续三轮，同一个形状：**

- **第 22 轮**：修 D2 移除门禁的正则（漏了连字符写法）。
- **第 23 轮**：发现第 22 轮**修复时写下的那段注释**在召回、精度、历史计数三处虚报。
- **第 24 轮**：发现第 23 轮**修复时写下的那段注释**的机制断言是假的 —— 它声称某个正则组「不能为空，否则本门禁自己的测试名会被匹配」；实测把那个组零宽化后，三个相关测试**一条都不红**，真正挡住那个测试名的是模式尾部的 `\b`。同一个 commit 的说明还声称这个设计选择「已被反例钉住」，而它挑中的用例恰好是相邻形态里**唯一钉不住它**的那一个。

第 23 轮那个 commit 的整个论点是「断言覆盖面的散文不会被执行，所以必须换成会跑的表」—— 然后它在同一个 commit 里新写了一条**不会被执行、且是错的**机制断言，还说它被表钉住了。**把散文换成表，不等于停止写散文**：剩下的那部分散文，恰恰是表覆盖不到、因而最需要这条纪律的部分。

**评审者怎么查**：读本轮 diff 里每一条新增的机制断言，逐条问「哪个用例钉住它」。

```sh
# 新增行里带因果连词的注释/文档，逐条读，不是逐条信
git diff <base>..HEAD | grep -nE '^\+.*(因为|否则|正是为了|不能|必须|otherwise|because|would make|so that)'
```

指不出用例的，按 F4（断言型陈述）记；指得出但没跑过变异的，要求当场跑一次。

## A. 变异测试（最高优先级）

这是最后一轮才首次系统性使用、并且一次性开出最多阻塞的手法。**它排在最前面。**

**做什么**：把被测函数掏空，跑它在台账（`docs/feature-status.yaml`）里声称的证据测试。

**怎么做**：

1. 从台账 evidence 里取出被引测试与它声称覆盖的函数。
2. 在被测函数体开头插入短路：
   - 有副作用的过程 → `if true { return }`
   - 有返回值的函数 → 直接 `return` 零值 / 空切片 / `nil`
   - 纯变换函数 → `return` 输入本身（恒等变换，比零值更隐蔽，也更接近真实退化）
3. 跑那条证据测试：`go test ./<pkg> -run '^<TestName>$' -v`
4. 收掉掏空的代码。

**第 2、4 步先过判别式，再决定用 `go test -overlay` 还是改工作树。**

> **判别式：被测代码（或那条证据测试）会不会在*运行时*从磁盘读源文件／文档？**
> 也就是测试进程里出现 `os.ReadFile` / `os.ReadDir` / `os.Open` / `filepath.WalkDir` /
> `parser.ParseFile` / `parser.ParseDir` / `exec.Command("go", "list", …)` 去读**仓库自己的文件**。
> - **不读盘** → 用 overlay。掏空只需在编译期可见，overlay 就够。
> - **读盘** → **overlay 无效，且失效是静默的**（测试照常绿），必须改工作树。

`-overlay` 只改变 **go 命令构建时看到的源文件**，不改变测试**进程运行时**从磁盘读到的字节，也不传播进它 fork 出来的子进程。凡是把源码/文档当**数据**读的门禁，overlay 里的掏空对它们**根本不存在**。

**`internal/archtest` 全体门禁属于「读盘」这一类，一条都不能用 overlay 探测。** GOV8 的 marker 扫描（`status_evidence_test.go` 的 `parser.ParseFile`）、GOV9 的 `buildGoSymbolIndex` / `liveDocs`、GOV2/GOV3/`removal_test.go` 的目录遍历，全部走 `moduleRoot(t)` + 读盘。

实测对照（同一份掏空、只差 overlay 与工作树）：给 `TestVSCodeExtensionRemoved` 开头插一条无条件 `t.Skip`，
`go test -overlay … -run '^TestLedgerEvidenceIsClauseComplete$'` 报 **ok**；同一处改动写进工作树，同一条命令
报 **FAIL: D2/O12: clause 1 bad evidence — …opens with an unconditional t.Skip(...)…**。
**本轮评审就是照原来那条无条件建议操作，据此开出了两条并不存在的阻塞。**

这条边界不靠人记：`internal/archtest/overlay_test.go` 的 `TestGateFilesReadFromDiskAtRuntime` 把它做成了机器判据，两个方向都测（列表里的门禁文件必须仍在读盘；新增的读盘门禁文件必须进列表）。

⚠️ **那个判据只扫 `internal/archtest` 这一个目录**（它 `ParseDir` 的就是这个包）。所以**别的包里新写的读盘测试不要往 `overlayImmuneGateFiles` 里加** —— 加进去会被当成死条目判红（`got` 里永远不会出现非 archtest 的文件名）。它们只能登记到下面这张表，那张表是人工维护的。

**已实测的「读盘 → overlay 无效」包**（这一列随实测增补，别凭印象加）：

| 包 / 文件 | 运行时读的是什么 | 结论 |
| --- | --- | --- |
| `internal/archtest`（全部门禁） | `moduleRoot` 下的 `.go` / `.md` / `docs/feature-status.yaml`，外加 `go list` 子进程 | overlay 无效 |
| `internal/vcs/seam_race_test.go` | `parser.ParseDir` 解析 `internal/vcs` 自己的生产源码（`TestPublicRepoWritersAcquireRepoLane`） | overlay 无效 |
| `internal/config/example_test.go` | `../../config.example.yaml` | overlay 无效（非 `.go` 文件，构建根本不看） |
| `internal/guard/verdictcatalog_test.go` | `parser.ParseFile` 解析 `internal/guard/guard.go` 与 `internal/execpolicy/policy.go` 的生产源码 | overlay 无效 |
| `cmd/gendocs`（`repoRoot(t)`） | `docs/**.md` 生成物 | overlay 无效 |
| `internal/skills`、`cmd/yanshi`（`repoSkillsDir`） | 仓库 `skills/` 下的 `SKILL.md` | overlay 无效 |

**已实测的「不读盘 → overlay 有效」包**（反例同样要写下来，否则这条判别式会被当成「一律别用 overlay」）：

| 包 | 为什么有效 |
| --- | --- |
| `internal/bootstrap`（GOV5/GOV7，`wiring_test.go`） | 全程用**进程内装配出来的** `App.ToolNames` 对账，零读盘 |
| `internal/ctxcompact`、`internal/guard` 等普通单测 | 断言只针对编译进来的代码行为 |

**改工作树时的还原纪律**：`cp <file> /tmp/<file>.bak` 备份 + 写回，或者 `git stash`。**别用 `git checkout -- <file>` 还原**——同一文件上先前的正式编辑会被一起回退，而且是静默的，这是有过事故的。

**什么算发现问题**：

- **测试仍 PASS = 证据无效。** 这条证据不证明任何东西，台账条目是虚报。
- 测试 PASS 且输出里有 `--- SKIP`：属于同一问题的**更隐蔽形态**，见下方实例。
- 只有部分子测试红：说明证据覆盖面小于台账声称的子句范围，按部分虚报处理。

**真实实例**：`internal/ctxcompact.EnforceToolCallPairs` 掏空后，台账 `E2/PROP1#3` **当时**引用的属性测试**一条不落全部 PASS**。原因：属性测试的前置条件守卫用**被测函数自己的产物**算 skip 条件，函数一掏空，每个 trial 都在守卫处 skip，而 `go test` 对 0 个执行 trial 报 PASS —— 与真正通过在退出码、在输出、在 CI 日志里都不可区分。

修复后的参考实现：`internal/ctxcompact/plan_property_test.go` 的 `runGeneratedProperty` / `minExecutedTrials` / `requireTrialFloor` —— 守卫（`skipAlreadyCompacted`）只读**生成的输入**、绝不读被测函数的输出，并且断言实际执行的 trial 数下限。

**参考实现的关键是作用域，不只是那个下限，而作用域收敛了两次。** 第一版只把这套守卫接进三条配对属性，函数名也叫 `runPairingProperty`（那个名字今天只作为改名记录出现在该文件的注释里，**不要照它去 grep**）—— **那个窄作用域本身就是缺陷**：被它漏在外面的两条属性（pin 集合子集、token 缩减）继续拿被测函数自己的产物当守卫，掏空后依旧全绿。第二版接进了 5 条，同时把描述从「窄」直接改成了「已经全覆盖」，而实际上还有 3 条在外，其中 2 条掏空后仍绿：`Run` 掏空成恒等 → `TestProperty_NoDoubleCompaction` 报 `--- PASS`；`Plan` 掏空成 `&PlanResult{}` → `TestProperty_NoEmptySummaryMessage` 报 `--- SKIP`。**修范围和改描述是两件事，别一起做。**

正确形态是**包内所有生成型属性一律走同一个入口**，包括跨文件的。核对方法是数两边而不是读文档：

```sh
grep -rhn '^func TestProperty_' internal/ctxcompact/ | wc -l    # 属性数
grep -rn 'runGeneratedProperty(t,' internal/ctxcompact/ | wc -l # 入口调用数
```

两个数相等才算全覆盖。形状确实不同的那条也接得进去：`TestProperty_EachSummaryCallWithinWindow` 的界是二维的（窗口大小 × 历史），做法是**嵌套** —— 窗口扫描在外、入口在内，它自己那条「除最小窗口外都必须 summarize 出东西」的内联下限与共享下限**并存**，因为两者抓的退化不同（共享下限抓「不再产生 trial」，内联下限抓「RunSummary 一律答 ErrNoWindowRoom」）。照第一版那个只接配对属性的形状实现，等于把已经判定过的缺陷复制回来。

这条约定**不是机器强制的**（理由见 ADR-0011 边界），只能靠本清单在评审时看。

**推论（写给被评审者）**：凡带前置条件守卫的属性测试，必须断言实际执行的 trial 数下限，并且这个下限要**统一在一个入口**上，不能按属性挑着加。

## B. 门禁探针（正反两向，缺一不可）

**做什么**：对每一道声称"会拦住 X"的门禁，实测它拦得住 X，且不误伤合法用法。

**怎么做**：

1. **正向探针**：在被扫描范围内造一个**应该被抓住**的违规，跑门禁，确认变红，读错误信息是否指向正确位置。
2. **反向探针**：造一个**形似违规但合法**的用法，跑门禁，确认不红。
3. 两个探针都跑完再删掉（`git checkout` / 删文件），确认工作树干净。

**只跑正向是半个探针。** 一道会误伤的门禁最终会被删掉，那比漏检是更大的洞 —— 所以反向探针不是可选项。

**什么算发现问题**：

- 正向探针全绿 → 门禁存在漏检，该门禁支撑的验收子句是虚的。
- 反向探针变红 → 门禁会误伤，它的寿命有限，等同于没有。
- 门禁红了但错误信息指不到具体文件/符号 → 按「可用性缺陷」记，不算阻塞但要记。

**真实实例**：`internal/archtest/removal_test.go` 的 `d2Mentions` 最初只有中文模式。本仓多份文档（README、`docs/vcs.md`、`docs/commit-convention.md`、若干 spec）是**英文正文**，一句英文的重新宣传可以全绿通过 —— 而 D2/O12 的第二条验收子句除这个测试外没有别的证据，**这条子句对最可能违反它的那批文档整体失效**。同时反向探针也必须过：`.vscode` 出现在忽略项列表里、`ide-vscode` 是提交 scope，两者都不是「这东西还在售」的声明，词级匹配会在两处误伤 —— 所以现在的模式刻意要求产品名与那几个词**相邻**。

### B1. 探针之前先把扫描面列出来（子条，不是独立手法）

**为什么要单列**：上面两条探针的措辞**预设你已经知道**这道门禁扫哪里 —— 而探针只在扫描面之内有意义。一个造在扫描面**外**的正向探针不变红，读起来和「门禁漏检」一模一样；一个造在门禁本就不该管的文件里的反向探针变红，读起来和「门禁误伤」一模一样。两种误诊的修法相反，而 diff 里看不出区别。

**做什么**：对每一道门禁，先把三件事写成一行，再造探针：

1. **扫哪些路径**（walk 的根是什么、`SkipDir` 掉哪些目录）
2. **扫哪些扩展名 / 文件形态**
3. **明确跳过什么**（测试文件？归档目录？gitignore 的外部素材？）

**怎么做**：这三件事只能从那道门禁的 `WalkDir` 回调读出来（`SkipDir` 那几个分支 + 后缀过滤那一行），**不要读它的注释**。列完**逐项各造一个正向探针**：每一个「应该被扫到」的路径下各放一次违规，确认都红；每一个声称跳过的目录下各放一次，确认都不红。**列表不能只列不试** —— 注释描述的扫描面与 walk filter 的实际行为不一致，在本仓发生过。

**什么算发现问题**：某个载体落在扫描面外，而它恰好是这道门禁要防的东西**最可能出现的地方**。

**真实实例**：D2 移除门禁只扫 `.md`，于是把那个已作废的交付物重新宣传进 `package.json`（`contributes` / `engines` 这些字段就是它的天然载体）对这道门禁**完全不存在** —— 门禁绿，宣传照发。同一个病在斜杠命令幻影门禁上连犯三次：`5eb5869` 只扫 markdown、`cf088f7` 只扫 Go 注释，两次都把离用户最近的 `config.example.yaml`（操作员照抄它建自己的配置）留在扫描面之外；接上多载体之后当场又抓出第四种载体（`internal/i18n/catalog/*.json` 里成套的 usage 字符串）。三次都不是正则写窄了，全是扫描面漏了一类文件。

### B2. 探针的输入必须来自被测系统，不能手写（子条）

**为什么要单列**：B1 管的是「探针放在哪」，这条管的是「探针里写了什么」。权限门禁这类
探针要喂一个**名字**（工具名、profile 名、路由路径），而手写的名字可能**根本不存在** ——
于是探针输出的是「这个名字没被授权」，你读成「这个已注册的工具没被授权」。

**判据**：`guard.Check` 对**任何**未命中 allow 列表的名字都返回 Prompt。所以
「不存在的工具」与「注册了但没授权」在探针输出里**逐字节相同**。凡是这种
「缺席与不存在同形」的门禁，手写输入必然产出幻影发现。

**怎么做**：反向遍历**注册表本身**，别正向喂名字。权限梯度就是
`for _, n := range app.ToolNames { if !allowed(n) { … } }` —— 一次列出全部真实缺口，
且不可能列出不存在的东西。同形态还有：路由探针遍历 server 的路由表而不是手抄 URL、
配置探针遍历结构体字段而不是手抄键名。

**什么算发现问题**：探针报出的名字在注册表里查不到 —— 这不是发现，这是探针自己产的
幻影，按误报撤销并更正已写下的记录。

**真实实例**：W1 那轮的权限梯度探针手写了一串工具名，其中 `shell_list` 是凭印象编的
（真名是 `shell_start` / `shell_read` / `shell_write_stdin` / `shell_wait` /
`shell_cancel`）。它被当作「已注册但要弹窗」记进了两份评审记录，跨三份文档传播，直到
后来那次遍历 `app.ToolNames` 的盘点才发现它从不存在。讽刺的是那一轮的主题正是幻影名 ——
**手写输入把幻影门禁探针变成了一台幻影发生器**。

## C. 测试名核对（这个陷阱在本项目骗过一次）

**做什么**：跑任何 `-run` 之前，先确认那个测试名真实存在。

**怎么做**：

```sh
grep -rn '^func Test' internal/<pkg>/ | grep <关键字>
```

确认名字逐字一致（大小写、下划线、子测试路径）后再跑 `go test -run`。

**什么算发现问题**：`go test -run <错名>` 匹配 0 个测试时**退出码是 0，输出行以 `ok` 开头**。任何只看退出码、只 `grep FAIL`、或只扫行首的检查都会把它读成通过。

具体分三种形态，**危险程度不同**（本条经两轮实测校正，不要凭印象记）：

| 形态 | 实际输出 | 可见性 |
|---|---|---|
| 顶层测试名写错 | `ok  <pkg>  0.155s [no tests to run]` | 有标记 |
| 子测试路径写错，且该测试**有** `t.Run` 子测试 | `ok  <pkg>  0.328s [no tests to run]` | 有标记，但 `-v` 下同时出现一条真的 `--- PASS: TestX` |
| 子测试路径写错，且该测试**没有** `t.Run` 子测试 | `ok  <pkg>  0.497s` | **完全无标记** |

第三行是实测出来的，第一版清单只写了前两行并断言「`grep '[no tests to run]'` 两种形态一网打尽」—— 那句话对第三行**失效**。复现：

```sh
# 命令必须收窄到那个函数体：整文件 grep 会数到别的测试的 t.Run，
# 照着读会得出「它有子测试」这个相反结论。
awk '/^func TestSSEEvent_Golden/,/^}/' internal/proto/frame_test.go | grep -c 't.Run'   # 0
go test -count=1 ./internal/proto -run 'TestSSEEvent_Golden/nosuchsub' -v
```

输出是：

```
=== RUN   TestSSEEvent_Golden
--- PASS: TestSSEEvent_Golden (0.00s)
PASS
ok  	github.com/x6nux/yanshi/internal/proto	0.497s
```

既没有 `testing: warning: no tests to run`，也没有 `[no tests to run]`，`=== RUN` 计数是 1 不是 0。**三种自动判据（退出码、`[no tests to run]`、`=== RUN` 计数）在这一格全部失效** —— 因为从 Go 的角度看确实跑了一个测试，只是那个不存在的子测试路径被无声忽略了。这一格最危险：它长得和一次真正的成功**逐字节相同**。

真正的陷阱在第二、三行：`TestX` 匹配上了、父测试体**真的执行并 PASS**，只有子测试被过滤掉。第二行的 `-v` 输出长这样：

```
=== RUN   TestReal
--- PASS: TestReal (0.00s)          ← 货真价实
testing: warning: no tests to run   ← 但断言一条没跑
ok  	tn	0.119s [no tests to run]
```

只盯 `--- PASS` 就会认定断言执行过了。多包 `go test ./...` 时更隐蔽 —— 标记只出现在不匹配的那一行，混在一堆 `ok` 里。

**判别方法**：分两步，第二步不能省。

1. **先核对名字真实存在**，这是唯一对三种形态都有效的判据 —— 顶层名去 `grep '^func Test'`，**子测试路径去 `grep 't.Run'` 核对那个子测试名真的被注册过**。第三种形态只有这一步能抓。
2. 再加 `-v` 数实际执行的测试：

```sh
go test ./<pkg> -run '^<Name>$' -v 2>&1 | grep -c '^=== RUN'
```

结果为 0 = 零匹配。用子测试路径时改数 `--- PASS`/`--- FAIL` 的条数，并与预期的子测试数对账 —— 父测试的那条 PASS 要减掉。

`grep '[no tests to run]'` 是**前两种形态**的省事办法，第三种形态它抓不到（见上表）。

**这条陷阱同时污染 A 和 B。** 变异测试用错名跑，会看到 `ok` 并错误地判定「掏空后仍通过 = 证据无效」；门禁探针用错名跑，会看到 `ok` 并错误地判定「探针没被抓住 = 漏检」。**两个方向都会产生假阳性指控。** 所以 C 必须在 A、B 之前执行。

### C-bis. 核查脚本本身必须先自证能命中已知真值

`-run` 写错名只是这类错误里最出名的一种。**任何为核查而临时写的脚本（shell 循环、`awk` 抽取、`grep` 计数）都属于同一类**：它对着真实语料跑出一个「零命中 / 全部 MISS / 计数为 0」的结果，而那个结果读起来正好就是一个重大发现。

**怎么做**：脚本写完，先喂给它一个**已知应当命中**的输入，确认它真的命中；再去跑全量。零成本，且是唯一能把「脚本坏了」与「代码坏了」分开的手段。

**什么算发现问题**：脚本报出的异常率高得离谱（「16 个引用全部 MISS」「这个表里一条都没有」），**先怀疑脚本**。

**真实实例（都发生在本仓，都长得像重大发现）**：

- shell 里用 `set -- $pair` 在 `while read` 循环中拆分字段 —— 每次比较都拿到空串，16 个符号引用**全部报 MISS**。真值是 0 个 MISS。**归因经复测更正**：不是「位置参数没更新」，而是**本仓默认 shell 是 zsh，而 zsh 不对未加引号的变量展开做分词**。复现：

  ```sh
  zsh  -c 'pair="a b"; set -- $pair; echo $#'   # 1  ← 整个 "a b" 成了一个参数，$2 为空
  bash -c 'pair="a b"; set -- $pair; echo $#'   # 2
  ```

  推论：任何从 bash 语料抄来的分词写法（`set --`、`for x in $list`、`$(...)` 展开成多参）在 zsh 下都会静默塌成一个参数。要分词就显式写 `${=pair}`，或干脆别用 shell 拆字段（`awk`/`python3` 更可靠）。
- 用 `awk '/开始/,/结束/'` 截取一段表定义，结束模式在表内部提前命中，截出来的片段只剩表头，于是表项**被数成 0**。

两次的正确做法都是同一句：先拿一个肉眼确认存在的条目喂进去，看脚本认不认。

## D. 空壳测试识别

**做什么**：逐条读证据测试的断言，判断它有没有可能失败。

**怎么做**：对每条被引测试问四个问题，各有对应的搜索手法。

### D1. 恒真断言

对字面量或对自己刚构造的常量断言。

```sh
grep -rn 'assert\.\|require\.\|if .* != ' internal/<pkg>/<file>_test.go
```

**判据**：断言两侧是否都不依赖被测代码的输出。像 `4/2 >= 2` 这种，无论被测代码怎么变都是真。

### D2. 吞错

```sh
grep -rn 't\.Logf\|t\.Log(' internal/<pkg>/*_test.go
grep -rn '_ = ' internal/<pkg>/*_test.go
```

**判据**：`err != nil` 分支里只有 `t.Logf` 没有 `t.Error`/`t.Fatal`；或返回值被 `_ =` 丢弃后再没被检查。**`t.Logf` 吃掉错误 + `_ = out` 是本仓出现过的组合形态。**

### D3. fake 太宽

**判据**：fake 是否检查了**关键入参**？还是不看入参、硬编码返回正确值？

一个不看 argv 的 fake 进程会让「argv 表写错」这类 bug 完全不可见 —— 无论被测代码把 argv 拼成什么，fake 都返回成功。

**真实实例**：`internal/tools/diagnostics.go` 的探针 fake 最初不看 argv，硬编码返回成功，**盖住 bug 达三轮**。修复后的形态见 `internal/tools/diagnostics_test.go`：fake 现在断言 `spec.Args` 与期望表逐项相等，argv 不匹配时**模拟真实二进制的拒绝**（返回 `flag provided but not defined` 与非零退出），并由 `TestDiagnosticsProbesEachToolchainWithItsOwnVersionArgv` 把每个程序的 argv 逐条钉住。

**通用判据**：**fake 必须拒绝真实实现会拒绝的输入。** 一个只会成功的 fake 不是 fake，是常量。

### D4. spy 只证明调用发生

**判据**：spy 记录了「被调用了」，但**结构上看不见**调用的后果 —— 子进程的环境变量、退出码、资源是否回收、goroutine 是否退出。

一个返回 stub 的 spy 让所有这些都不可观测。判别方法：问「如果被测代码把环境变量传错/不回收子进程，这个 spy 会红吗？」答案是「不会」就是 D4。

**什么算发现问题**：以上任一命中，该测试不构成证据，台账里引用它的子句按虚报处理。

## E. 不会被执行的测试

**做什么**：确认每条证据测试在默认 `go test ./...` 下真的会编译并执行。

**怎么做**：逐项排查五种形态。

| 形态 | 检查命令 | 说明 |
|---|---|---|
| `testdata/` 下 | `find . -path '*/testdata/*' -name '*_test.go'` | Go 工具链完全忽略 `testdata/` |
| 文件名式 GOOS/GOARCH 约束 | `ls internal/<pkg>/*_test.go` 看后缀 | `foo_windows_test.go` 在 darwin 上**不编译**，且不需要任何 `//go:build` 注释就生效 |
| `//go:build` 约束 | `grep -rn '//go:build' internal/<pkg>/` | `e2e_real` 等标签下的测试默认不跑 |
| 无条件 `t.Skip` | `grep -rn 't\.Skip' internal/<pkg>/` | 函数体开头就 skip，`go test` 编译它、运行它、报它通过 |
| 条件 skip 导致 0 trial | 见 A 的实例 | skip 在子测试闭包里，条件由被测函数的产物算出 |

**权威判据**：`go test ./... -run '^TestZZNonexistent$' -v` 不会告诉你哪些编译了。用这个代替：

```sh
go test ./<pkg> -run '^<TestName>$' -v 2>&1 | grep -E '^(=== RUN|--- (PASS|FAIL|SKIP))'
```

没有 `=== RUN` 行 = 没跑（可能是零匹配，见 C；也可能是文件根本没编译）。有 `--- SKIP` = 跑了但没断言。

**什么算发现问题**：证据测试落在以上任一形态 → 它没有在默认 CI 路径上验证过任何东西。文件名式 GOOS 约束**尤其容易漏**：它不需要注释行就生效，而只扫 `//go:build` 的检查看不见它（本仓的 GOV8 曾因此文档比实现强了一档，见 ADR-0011）。

## F. 文档虚报扫描

本仓已抓到多处。**这类问题有两种形状：写下的那一刻就是错的，和写下时是对的、之后无声腐烂。** 两种本仓都抓到过，**别默认是第二种** —— F1 的头号实例就是一次「把第一种误判成第二种」，而那次误判又被当成第二种的证据写进了本清单。

**做什么**：对文档里每条**事实型断言**实际去数、去跑、去查。不要读着像对就放过。

**怎么做**：按五种形状分别扫。

### F1. 具体计数

**扫法**：`grep -rnE '[0-9]+ ?(处|条|个|项|files?|places?)' docs/ CLAUDE.md`

对每个数字实际数一遍。但**先分清「数错了」和「腐烂了」再下结论** —— 本条的论点是：**一个不写口径的数字无法被复核**。同一个对象换一种数法就是另一个数，复核者拿自己的口径量一遍，既可能把从没错过的数字判成腐烂，也可能把真错了的数字判成没错。**这两种误判里前一种比较出名**（「文档里的数字迟早会腐烂」几乎是条常识），于是「腐烂」成了复核者的默认答案 —— 而它只是**两种误判之一的结论**，不是这两种误判的上位概念。上一版这里写的是「腐烂只是这两种误判里比较出名的那一种」，把一个**现象**塞进了「误判」的枚举位，读起来对、按字面推不通。

**真实实例（均为历史发现，第一条是本条论点的来源，也是「计数必然腐烂」的反例）**：

- CLAUDE.md 里 `exec.Command*` 的处数曾被一次自我更正判为「写下时是对的、后来腐烂了」，本清单据此把它当作 F1 的头号论据。**实测证伪**：那两个数是**两种口径**（排掉纯注释行的「调用点」，与不排注释行的行数），而原句用的词就是调用点 —— 那个数在它自己的口径下**从未错过**。裁定与两条复算命令见 `CLAUDE.md` 的「子进程发射」段。**撤回写进 CLAUDE.md 之后，本清单这一侧又被编辑过几轮才跟上，其中一轮正是重写整个 F 段论证的那次** —— 这正是 F3 末尾那条「改名时要 grep 的不只是名字，还有围绕它的那段描述」的同形复发。
- 拆解文档写「`Evidence` 11 字段」，实测 10 —— 而**该条自己的枚举（4 已断言 + 5 未断言 + `LogArtifactID`）恰好也等于 10**，也就是同一句话里数字与枚举自相矛盾，只是没人把两边加起来。**这一条写下的那一刻就是错的**，与腐烂无关。
- 某处「5 条 partial」实测是 12。

**判据补充**：一条计数断言如果同一段里**还附了明细枚举**，先把枚举数一遍再看数字，这两者对不上就是发现。**这条对本清单自己也成立，而且抓到过** —— 见 F 段末尾那张三档表下方的判据，它建立三档的同一段里，枚举、断言、举证曾是三个互不相等的数。

**结论倾向**：文档里的精确计数应当**改成不带数字的描述**，或改成「由 `<某命令>` 打印」。**后者才是本条真正要的东西**：它不承诺数字永不改变，只承诺读者能当场复算出写这句话的人用的是哪个口径。留一个裸计数，等于要求后来的每一个复核者都猜对你的口径 —— 猜错的那次会以「发现腐烂」的形式出现，读起来和真发现一模一样。

### F2. 描述另一个文件当前内容的句子

**扫法**：找形如「X 文件里写的是 Y」「台账文件头写 `""`」的句子，逐条打开那个文件核对。**否定式（「X 文件完全没有 Y」「参数表里没有任何 Z」「零处构造 W」）算同一类，而且更危险** —— 肯定式写错了读者一打开就看见，否定式写错了没人会去开那个文件确认「它确实不在」。

**`.github/workflows/*.yml` 是这一类里的高价值目标，优先扫。** 关于 CI 的句子（「CI 会跑 X」「没有任何作业设置 Y」「这个 tag 只用于构建」）几乎全是描述另一个文件当前内容，而**没有任何门禁对账 workflow 与文档中关于 workflow 的陈述** —— CLAUDE.md、拆解文档、台账证据栏都在描述 CI 干了什么，改 workflow 的人不会回头改它们。判据同上：肯定式当场打开 `ci.yml` 核对，否定式必须附上产出空输出的那条 grep **和一条命中的负向对照**（证明模式本身没写窄）。**真实实例**：拆解文档 W5 那条曾写「全仓 grep `nokeyring` 只命中实现文件与注释」，实测还命中 `internal/cli/doctor.go` 的生产字符串与 `.goreleaser.yaml`/`ci.yml` 里真实的 tag 传递；承重结论（那半个实现从未被执行）成立，靠的却是另一句 —— 「没有任何 workflow 跑 `go test -tags=nokeyring`」，那句才是能附空输出 grep 的形态。

**真实实例**：

- 某处文档描述了台账文件头的当前措辞，而台账在**十几分钟后**就被改了 —— 这类句子的半衰期以分钟计。
- 拆解文档断言「`config.example.yaml` 完全没有 `subagents:` 段」，实测那段一直都在，连合法范围都写了，而且有一条**绿测试**（`internal/config::TestExampleConfigDocumentsSubagents`）正面钉着它。该条据此把缺口记成三处，实为两处 —— **虚增的缺口会直接变成工作包**。

**结论倾向**：改成引用（「见 `<路径>` 的文件头」），不复述内容。否定式断言必须当场附上那条 grep 与它的空输出，否则不进结论。

**这两类目前没有、也不会有门禁 —— 这是实测结论。** 曾评估过给拆解文档加一道「否定式存在断言 + 字段计数」的门禁，两边都不成立：

```sh
# 分母现算，别信写死的数字
python3 - <<'PY'
import re
lines=open('docs/superpowers/acceptance-breakdown.md',encoding='utf-8').read().split('\n')
neg=re.compile(r'完全没有|没有任何|不含|零处|零个|全仓无|无任何|找不到|不存在|从不|从未')
print('带否定标记的行:', sum(1 for l in lines if neg.search(l)))
PY
grep -nE '[0-9]+ ?(个)?字段' docs/superpowers/acceptance-breakdown.md | wc -l
```

- **字段计数**：分母**现在已经是 0** —— 拆解文档的写作纪律（「字段/元素计数一律不写数字，改写枚举或『见 `路径::符号`』」）把它们全清掉了，上面那条 `grep` 现跑零输出。当初评估时分母也只到个位数，且失效那条写的是裸类型名（`Evidence`）不带可解析路径前缀，机器根本判不出指的是哪个 `Evidence`。要机检就得先强制改写成 `路径::符号 的 N 个字段` 这种带锚点的形式 —— 那是约定变更，门禁只能覆盖已经改好的那部分，对新写错的那条依然无效。**结论只被加强：一道分母为 0 的门禁不值得存在；按 F1 直接把数字删掉更彻底**（上面那条实例就是这么修的，而且已经推广成了写作纪律 —— 这正是「改约定」而不是「加门禁」的收益）。
- **否定式存在断言**：带否定标记的行是三位数，其中**形状上可机检**（反引号文件名 + 相邻否定词 + 反引号字面量 needle）的只有个位数，其余全是语义性的（「零生产调用点」「没有任何一处写进 slog」「链路断两刀」）—— 这些要判真伪得先做一次带测试文件过滤的全仓引用分析，不是 grep 能干的事。一道召回率个位数百分比的门禁**比没有门禁更坏**：它会让「跑过门禁了」变成不再人工扫这一类的理由，而这正是 B 段说的「只跑正向是半个探针」的同一个病。**外加自指陷阱**：撤回一条否定式断言时，撤回文本本身含有那个断言的原文，门禁会当场把撤回判红，于是又要一张 `d2HistoricalDocs` 式的墓碑表 —— 为个位数召回率养一张豁免表，成本高于收益。

所以这两类**明确留在人工侧**，由本条负责。

### F3. 行号引用

**扫法**：`grep -rnE '\.go:[0-9]+' docs/ CLAUDE.md`

**判据**：行号在任何一次插入删除后失效，且失效**无声**。改用**符号引用**（函数名、类型名、常量名）—— 符号改名时 `grep` 找得回来，行号漂移找不回来。

**但「找得回来」不等于「有人去找」。** 这条规则第一个栽在自己身上：本清单 A 段的参考实现指针写下 6 个提交后被一次改名作废，而那是该约定的唯一指针，没有任何人回来 `grep`。**符号引用去掉了无声的数字漂移，换来的是同样无声的名字漂移** —— 而且更坏，坏掉的名字读起来是合法的。

所以现在这一半是**机器强制的**：`internal/archtest/docsymbols_test.go::TestGOV9DocSymbolReferencesResolve`（GOV9）扫活文档里所有 `路径::符号` 引用，路径解析得出、符号解析不出即判红。三条使用约定：

- **要引用就写全 `路径::符号`**，只写反引号里的裸符号名不受门禁保护。
- **要故意写一个不存在的名字**（记录幻影、给模板占位、举反例），就**不要带可解析的路径前缀** —— 门禁只在路径解析得出时才追究符号，这既是自指逃生门，也顺手把别的语言的 `::`（Rust 路径、pytest node id）挡在外面。
- **门禁不管非 Go 引用**（`*.yml` / `*.sh` / `*.toml` 里的 key、变量名、小节标题），那些没有 Go 符号可指，仍然只能靠本条人工扫。**但载体不等于引用类型**：台账 `docs/feature-status.yaml` 虽是 `*.yaml`，它的注释里写的是 Go 符号引用，现在**在扫描范围内**（`internal/archtest/docsymbols_test.go::ledgerDoc`，由 `internal/archtest/docsymbols_test.go::TestGOV9ScansTheLedger` 钉住）。这一条是评审探针逼出来的：往台账追加一条路径解析得出、符号不存在的引用，GOV9 报 `ok`；同一行文字放进任何活 `.md` 立刻变红 —— 也就是说台账里的符号引用当时**一条都没被保护**。⚠️ 顺带纠正一个似是而非的归因 —— 它已经**连续错了三次**（评审指控、实现者写进门禁注释、本清单上一版的更正），三次的结论对错各半，机制则每次都不同：台账里那批**缩写前缀**（`bootstrap.go::Build` 这种）既不是「路径解析不出所以被丢弃」，做这件事的**也不是 `deglued`**。真正的机制是 `internal/archtest/docsymbols_test.go::candidates` 对 `.go` 结尾的路径做**文件路径后缀匹配**（`strings.HasSuffix(f, "/"+path)`），裸文件名因此自己就锚得到 `internal/bootstrap/bootstrap.go`。`internal/archtest/docsymbols_test.go::deglued` 是**下划线粘连前缀**的重锚层，它对不含 `/` 的路径直接返回 nil，其 doc 注释明文声明「一个故意写的幻影裸文件名**绝不能**被重锚到树里某个真文件上」—— 把功劳记给它正好记反。实测（把台账里每一条缩写前缀逐个喂给 `candidates` 与 `deglued`，并附带一个已知能解析的全路径与一个已知不存在的裸文件名做自证）：缩写前缀**全部**由 `candidates` 命中、`deglued` **一律**返回空。**推论写给写文档的人：只要路径解析得出，这条引用就受保护 —— 缩写前缀 + 一个不存在的符号会当场判红，它不是逃生门；唯一的逃生门是不带可解析路径前缀的裸符号名**（与上面第二条一致）。当时不被保护的唯一原因就是那个文件根本没进扫描面。台账里的 `file:line`（非 Go）仍在门禁之外，本条仍要人工扫。

  ⚠️ **这一条同时是 GOV9 自身盲区的实例**：GOV9 只判「符号存不存在」，判不出「符号存在，但它干的不是这句话说的那件事」。上一版更正引用的 `deglued` 确实存在，门禁全绿，错的是描述。凡是把机制归给某个具体符号的句子，都要打开那个符号的实现读一遍再写。
- **`::符号` 简写形式同样不受保护。** 「同一行前面已经写过路径，后面只写 `::Sym`」是本仓第三种写法，而门禁的正则要求 `::` 前至少有一个路径字符，所以这些**一条都不扫**。它们既不是受保护的 `路径::符号`，也不带裸名那个「我故意说一个不存在的东西」的信号 —— 是三种形态里最容易被误以为安全的一种。本条扫到时按裸名对待：逐个去 `grep` 它到底存不存在。
- **强调排版被剥离后再判决，这是修了两次才成立的。** 门禁曾经有一个「`路径::符号*` = 前缀匹配」的形式，而 markdown 加粗是 `**`，于是 `**路径::符号**` 的收尾星号喂进那个捕获组，把名字悄悄降级成前缀，再去命中任何以它开头的真符号 —— 一次纯装饰性的加粗就能让一条引用永久失去保护。删掉那个形式只修了**星号**那一半：`*` 不在路径字符类里，正则遇到它自然停住。而 markdown 的强调字符**只有 `*` 和 `_` 两个**，`_` 恰好是路径字符类里唯一的那个 —— `_路径::符号_` 的前导下划线被吸进路径捕获，路径解析不出，整条引用被当作「不是本模块的引用」**无条件丢弃**，比降级成前缀更彻底。第一版探针枚举了三种星号形态，漏掉的正是唯一另一种可能出错的字符。现在的做法是**匹配前先按词法剥掉强调定界符**（`internal/archtest/docsymbols_test.go::stripMarkdownEmphasis`，只保留词内下划线，因为 `plan_property_test.go` 这类路径靠它），正向探针把两个强调字符的全部拼法连同其余装饰形态（`~~`、HTML 标签、代码跨度、链接、引用块、四种列表符号、表格、标题、中西文标点）逐条钉住，反向探针钉住词内下划线不被误伤。**唯一被改写但判决不变的形状是 glob 路径**（`tools/*.go::Foo` 的星号会被剥掉，剥前剥后都解析不出），这一条也按「判决不变」而不是「文本不变」钉住了。

**裸反引号符号名的缺口收不了，这是实测结论不是偷懒。** 曾经试算过一道「反引号里的 `Test*` 名必须在模块里声明」的门禁 —— 它正好能抓住 F3 自己栽过的那种跟头。实测（分母是活文档里全部反引号 `Test*` 名，用下面这条命令现算，**别信任何写死的数字**：一次评审里光是新增几个测试引用就让它涨了 5）：

```sh
for f in $(find docs -name '*.md' -not -path 'docs/superpowers/plans/*' \
    -not -path 'docs/superpowers/notes/*' -not -path 'docs/superpowers/specs/*' \
    -not -path 'docs/reference/*') CLAUDE.md; do
  grep -ohE '`Test[A-Za-z0-9_]*`' "$f"
done | sort -u | wc -l
```

解析不出的那几个**同样要现算，分子和分母一起**（把上面那条命令的输出跟 `grep -rhoE '^func Test[A-Za-z0-9_]*' --include='*_test.go' .` 做差集）。**分子写死是本清单自己栽过的跟头**：分母已经按 F1 改成现算了，分子却还留着一个硬编码的「5 处」，而那一次实测是 6。

现算出来的每一个都要人工判一次「活指针还是记录」。上一次实测时，现算出来的**每一个**都是正当写法、零真阳性，形态有四类：

- **故意写的旧名**（改名记录里引用改名前的名字）
- **计划与实现的偏差记录**（计划要求过某个名字，实现时改成了别的）
- **示意占位**（清单与 playbook 里的 `TestX` 之类）
- **不是测试函数的真实 Go 符号**（比如一个以 Test 开头的类型名），以及**裸 `Test` 本身** —— `CLAUDE.md` 里 goalloop 的三个评估器叫 `Test`/`Intent`/`Quality`，那是正当写法。最后这一类是硬编码「5」漏掉的那个。

结论：在本仓，一个**裸的、解析不出的符号名**最常见的用途本来就是「故意说一个不存在的名字」。带路径前缀时，写不写前缀就是那个「我确实指着它、它应该存在」的结构性信号；去掉前缀，这个信号也一起没了，机器无从区分死指针与诚实的历史记录。所以这一半**只能靠人工**：本条扫到裸符号名时，判断它是「活指针」还是「记录」，是活指针就补成 `路径::符号`。

**这个缺口刚刚又抓到过一次**：一次改名把 `internal/ctxcompact` 的属性测试入口改了名，同一个提交只修了清单这一侧，ADR-0011 与拆解文档里的两处裸符号指针原样留着 —— GOV9 全程绿。更糟的是 ADR 那句连**设计描述**也是旧的（它按改名前的窄作用域描述参考实现，而窄作用域本身就是被判定过的缺陷），跟着它走的人会把缺陷重建一遍。**改名时要 grep 的不只是名字，还有围绕它的那段描述。**

📌 已归档的带日期文档（`docs/superpowers/` 下的 plans / notes / specs）不在扫描范围内 —— 理由同 `d2HistoricalDocs`：改写历史记录去追一次改名，本身是另一种不诚实。

### F4. 断言型陈述（最危险）

形如「X 是 Y」「边界是 Z」的架构断言，读起来权威，但从没有人实测过。

**扫法**：找文档里所有关于**安全边界、隔离、强制点、唯一入口**的陈述，逐条设计实验去证伪。

**真实实例**：某处曾断言隔离边界是 guard 层加网络策略 —— 实测**证伪**，随后有两次提交专门收回这类陈述（`c1500ae` 停止把某个已死端口的代理称作被强制的边界；`ca08d9f` 停止断言出口流量被阻断）。

**判据**：一条安全性断言如果**没有测试钉着它**，它就是一句愿望。要么补测试，要么把断言降级成「意图」并写明当前实际状态。

### F5. 幻影引用

见 H。

**什么算发现问题**：任一条事实型断言与实测不符 → 阻塞。

**注意本清单自己也受 F 约束 —— 而这条自我约束本身改写过一次，因为上一版是假的。** 上一版写的是「本文件刻意不写任何关于其他文件当前内容的计数」，而本文件当时至少有四处这样的数字：GOOS 后缀测试文件数、台账某条 evidence 的属性测试条数，以及「反引号 `Test*` 解析不出几个」前后两处。最后那两处尤其难看 —— 上一句刚把「分子写死」判为本清单自己栽过的跟头、把 5 改成 6，下一段紧接着又把 6 写死了一遍，而分母那半已经改成现算了。**一段以「硬编码数字必然腐烂」立论的文字自带写死的数字，是本仓反复出现的形状**（另一例：GOV9 的 `internal/archtest/docsymbols_test.go::TestGOV9ScansTheLedger` 注释，同一轮一起修的）。

这条自我约束是本清单说服读者「我自己也过了这把尺子」的唯一凭据，所以它必须写成真的。真正的约束分三档：

| 档 | 形态 | 判决 |
|---|---|---|
| **现状计数** | 「另一个文件现在有 N 个 X」 | **禁止**。改别的文件就能让它变错，而没人会回来改本文件。 |
| **历史快照** | 「某轮评审报 10，那一轮实测是 8」 | **允许，且不许删数字**。实例的教学价值就在这两个数的落差上，删了就退化成空泛告诫。但必须带时间锚点（某轮 / 当时 / 第一版 / 上一次），让句子断言的对象是一次**已经冻结的测量**而不是当前状态。 |
| **量级 + 现算命令** | 「分母是个位数」「带否定标记的行是三位数」，紧跟一条可重跑的命令 | **允许**。不承诺精确值，且自带复算手段。 |

**判据**：一个数字，如果**改动别的文件就能让它变错**，而句子又没有把它锚在某一次具体测量上，就是违规。上面枚举的那几处，修法是**逐处判档**而不是「一律改成现算」，因为它们并不落在同一档：`Test*` 那处的分母本来就已经是现算的（第三档），而「某轮评审报 10 个 GOOS 后缀测试文件、那一轮实测是 8」那种实例**根本现算不出来**（第二档）—— 它记录的是一次已经发生的错误，不是一个可重算的量。

⚠️ **这条判据自己也栽过一次，形状正是 F1 的判据补充**：它上一版写「选『加限定』而不是把**三处**都改成现算」，而同一段的枚举是四处、那一轮实际改的也是四处、理由子句举的又只有两处 —— 枚举、断言、举证三个数互不相等，全落在这张三档表刚立起来的那一段里。**同时它当时是用「L46 那种实例」指认的那一档** —— 一个指向本文件自身的行号，而 F3 的整条论点就是行号会在任何一次插入删除后无声失效；GOV9 只扫 `路径::符号`，F3 自己的扫描模式是 `\.go:[0-9]+`，两道机制都看不见这种自引用。现在改成按内容指认。

## G. 接线激活的路径要当新代码审

**做什么**：找出本轮把「已写但没接进组合根」的代码接活的改动，把被接活的路径**当全新代码从头审**。

**怎么做**：

1. 找接线点：`internal/bootstrap` 里新增的 `Build*` 调用、新绑定的 context 注入器、新增的 factory 绑定。
2. 对每个被接活的分支，问：**这条路径以前从没在生产里跑过，回落路径才是一直在跑的那条。**
3. 重点查四类（都是子进程/资源类）：
   - **环境**：新路径是否传了 `PATH` / `HOME` / 工作目录？回落路径继承了进程环境，新路径可能从零构造。
   - **返回值**：新路径是否真的把退出码/错误传回去了？以前不可达的分支里可能有死代码。
   - **资源回收**：`Wait` / `Close` / `cancel` 在**每一条**退出路径上都调了吗？
   - **取消与超时路径**：成功路径修好了，不等于取消路径修好了。

**什么算发现问题**：被接活的路径上任一条与回落路径行为不一致，且没有测试覆盖该差异。

**真实实例**：`shell_run` 从直接 pipe 改走 `SecureProcessFactory` 后，一次接线暴露出三个从没跑过的缺陷 —— 子进程没有 `PATH`/`HOME`、退出码 footer 是死代码、**从不调 `Wait`**（每次 `shell_run` 漏一个未回收的子进程）。而且第一次修复只覆盖了成功路径：**流式错误路径**（也就是 TUI 按 Esc 取消、`timeout_s` 到期离开该函数的那条路）仍然直接 return，子进程和抽管道的 goroutine 一起永久驻留。唯一覆盖它的测试用的是 spy（见 D4），**结构上看不见这些**。当前形态见 `internal/tools/shell.go` 里 `reap` 闭包 + `defer reap()` 那段以及它上方的注释。

## H. 幻影名扫描

**做什么**：配置、文档、profile、注释里出现的每一个工具名、字段名、路径、环境变量名，`grep` 确认真实存在。

**怎么做**：

```sh
# 从 config.example.yaml / profiles / 文档里抽出所有名字，逐个：
grep -rn '"<name>"' internal/ --include='*.go'
# 零结果 = 幻影
```

对工具名，还要确认它**被注册**（不只是字符串存在于某处注释里）。本仓有 GOV5/GOV7 两道门禁做这件事，但它们只覆盖 orchestrator profile 与 guard 的免提示集 —— **文档里的名字不在门禁范围内**，必须靠本条手动扫。

**什么算发现问题**：

- 名字在配置/文档里出现但代码里不存在 → 幻影。**幻影让 profile 读起来比实际权限宽**（一个 allow 条目不对应任何真实工具），或让文档承诺一个不存在的能力。
- 名字存在但**没被注册** → 同样是幻影，只是藏得更深。

**真实实例**：

- `http_request` 是文档里的幻影工具名 —— 真实注册的是 `web_fetch` 与 `web_search`（`internal/tools/web.go` 里的注册调用）。**注意扫这个名字时会命中本文件这一行**：一份记录幻影名的文档本身就是该名字的一次出现，`grep` 的结果要减掉清单自己，否则会把「已清理」误读成「仍存在」。这正是 F2 说的那种自指陷阱。
- `rlm_query` 曾是 profile 里的幻影名，在 `c1cb3db`（`fix(bootstrap,docs): kill the rlm_query phantom name...`）里被消掉 —— 同一个提交还顺带修了四条台账条目的过度声称。**幻影名和台账虚报是同一种病。**
- `fs_mkdir` 曾残留在 guard 的免提示自动批准集里，白占一个「不弹窗」的槽位 —— 这是幻影名里**最危险的一种**：它带授权语义。

## I. 竞态与资源

**做什么**：跑 race detector，并单独验证取消/超时路径。

**怎么做**：

```sh
go test -race ./internal/<改动的包>
```

- 真实 race 会**稳定复现**（连跑 3 次全挂）；时序 flake 通常重试即过。判别方法：`for i in 1 2 3; do go test -race ./internal/<pkg> || echo FAIL; done`。3/3 挂 = 真 race，不是 flake。
- 取消/超时路径**单独验证**，不要假设成功路径的修复覆盖了它：
  - 子进程被回收了吗？（`Wait` 被调用）
  - goroutine 退出了吗？（抽管道的那些最容易漏）
  - `context` 取消后有没有仍在写的 channel？

**什么算发现问题**：

- `-race` 稳定报警 → 阻塞。
- 取消路径上有 `return` 绕过了资源回收 → 阻塞，即使成功路径已经修好。**这正是 G 的实例里第二次才发现的那种。**

## J. 两端契约的连通性

**本条是第 22 轮新增的**（见文末「本尺子的修订记录」）。加它的理由是一个**结构性盲区**：A–I 全部是静态 + 单元级的手法，检验的都是「某个已存在的断言是否成立」，**没有一条检验「两端各自都对、但中间没接上」**。而这恰好是本仓审计判定的**主导失效模式**（原文：「零件造好了，总装线没接上」）。

**做什么**：对每一种跨层契约载体，在**排除 `_test.go` 之后**分别数生产者与消费者，任一侧为 0 即为死契约。

### J 为什么不是 A、G、H 的重复

- **A（变异）打不到。** 两端各有有效测试时，掏空任一端，那一端自己的测试会红 —— A 判它们「健康」，而这个判决**是对的**：那两条测试确实有效。「单测有效」和「链路连通」是两件事，A 只回答前一个。
- **G（接线激活的路径）打不到。** G 的第 1 步是找**本轮**新增的接线点。从来没接上过的、以及早先接上后被断开的，那一步就扫不到。
- **H（幻影名）打不到。** H 只查名字存不存在、注册没注册。一个真实存在、真实注册、却零消费者的名字，H 判它合格。

机器侧同样有缺口：GOV4 判「`Build*` 从 `Build` 可达」（只在组合根内部），GOV5/GOV7 判「profile 与免提示集里的名字已注册」（只查注册，不查消费）。**只有 GOV6（`internal/archtest/ctxinject_test.go::TestGOV6ContextInjectorsHaveCallSites`）是「生产者/消费者连通性」这个形状** —— 它要求每个 `With<X>(ctx, …) context.Context` 注入器都有生产调用点，否则整条消费链静默读零值。

**所以 J 不是新发明：GOV6 就是这条手法已被验证有效的实现范式**（`registry.WithRole` 正是被它抓到的空跑）。J 只是把那个形状从 context 注入器**推广到帧类型、事件类型、回调字段** —— 缺的从来不是方法，是没人去别的载体上数一遍。

### 怎么做

载体清单（至少这三类，核查后可增补）：

| 载体 | 生产者 | 消费者 |
|---|---|---|
| `proto.ServerFrame` 的 `Type` 常量 | `proto.New*` 构造函数的调用点（`internal/proto` 之外） | `case "<type>"` 分发分支（TUI 的 `applyEvent`、`internal/api/v1`、`sdk/`） |
| `work.EventKind` | `work.Event{Kind: …}` 字面量 | `case work.Event*` 分支 |
| `TurnOpts` 里的回调字段 | 结构体字面量里的**赋值**（`字段:` 或 `x.字段 =`） | 字段的读取处 |

```sh
# 生产者：构造入口的调用点。排掉测试，也排掉定义所在包（那里只有定义）。
grep -rn 'proto\.NewPlanUpdate(' --include='*.go' internal cmd \
  | grep -v '_test.go' | grep -v '^internal/proto/'
# 消费者：分发分支。
grep -rn 'case "plan_update"' --include='*.go' internal cmd sdk | grep -v '_test.go'
# 回调字段的赋值点 —— 冒号式（结构体字面量）与等号式（后赋值）两种写法都要。
grep -rnE 'EmitWorkFrame\s*[:=]' --include='*.go' internal cmd | grep -v '_test.go'
```

`grep -v '_test.go'` **不是可选的**：每一种载体都有自己的单测，不排掉的话每一条的两侧都是非零，整张表全绿。

LSP 等价物比 `grep` 准（能区分定义与引用）：对构造函数用 `findReferences`，把结果里的 `_test.go` 与定义所在包剔掉。

### 三条执行纪律

前两条是本轮实测踩出来的，第三条是 C-bis 的直接推论。

1. **数字面量不等于数生产者。** 本轮第一版扫描直接数 `"plan_update"` 这个字符串在全仓的出现次数 —— 把 `work.EventKind` 的常量定义、guard 的模式词表、SSE 的 case 列表全算成了「生产者」，同时因为排掉 `internal/proto/` 而把**真正的**构造函数调用点排掉了。**两个方向同时错，而那张表读起来完全正常。** 要数的是构造入口的调用点。
2. **`ClientFrame` 和 `ServerFrame` 不能混在一起数。** 两者都有 `Type` 字段、都用 `New*` 构造，而 client→server 的帧「TUI 里没有 case 分支」是正常形态 —— 混着数会凭空造出一整批假的「无消费者」。按返回类型分开：`func New\w+\([^)]*\) ServerFrame`。
3. **抽取脚本先自证。** 用正则从构造函数体里抠 `Type: "…"` 字面量的脚本，会漏掉**用常量而不是字面量**写的那些（`internal/proto/frame.go::SubagentEventType` 就是），而本轮漏掉的那一条恰好是个零消费者的死契约 —— **脚本漏得越多，结论读起来越干净**。自证方法：把脚本数出的构造函数个数与 `grep -cE 'func New\w+\([^)]*\)\s*ServerFrame' internal/proto/frame.go` 对账，差值逐个打出来看。

### 什么输出算发现问题

- **任一侧为 0** → 死契约。
- **一侧为 1，且那个唯一的生产者自己在一条断链上** → 同样是死契约，只是要多跳一次。**这是最容易漏判的形态**：`plan_update` 的生产者计数是 1（`internal/agent/orchestrator/workevents.go::workEventFrame` 里的那次构造调用），读起来完全正常 —— 但它的**唯一**调用者是 `TurnOpts.EmitWorkFrame` 回调，而那个字段零赋值，于是有效生产者是 0。**判据：生产者计数为 1 时，必须再往上追一跳。**
- 两侧非 0 但全部落在同一个包内 → 契约没有跨层，按可疑记，读一遍确认。

### ⚠️ 阻塞门槛（这条不能省）

> 死契约**只有**在以下两种情况下构成阻塞：
>
> **(a)** 它被引作某条**终态**（`done` / `removed`）台账条目的证据；
> **(b)** 有**活文档**声称它能用。
>
> 否则它只是一条诚实的 `partial` 台账项，属于对应工作包的待办，**不是当前工作包的阻塞**。

理由：当前工作包的契约是「**它声称做完的事是真的**」，不是「仓库里一切都能用」。J 是一把扫全仓的尺子，而工作包是分片的 —— 把每条死契约都记成阻塞，等于让每个工作包为全仓的未完成状态负责，「干净」于是再次成为不可达目标，也就重演了本清单立起来要防的那件事。**J 扫出来的绝大部分应当流向台账与后续工作包，只有落进 (a)(b) 的才回到本轮阻塞列表。**

### 真实实例（本仓，第 22 轮实测）

「计划可流式更新」这条能力**两端各自齐全**：`internal/proto/frame.go::NewPlanUpdate` 构造帧，`internal/cli/tui/entries.go::planUpdateEntry` 渲染条目，**两端都有真单测** —— `internal/proto::TestNewPlanUpdateNilRowsIsNonNilEmptyChecklist` 与 `internal/cli/tui::TestPlanAndChecklistUpdateEntry_Render`。链路却断两刀：

1. `internal/agent/orchestrator/orchestrator.go::TurnOpts` 的 `EmitWorkFrame` 字段**全仓零生产赋值点** —— WS 与 SSE 都没接，`workEventFrame` 造出来的帧发不出去。
2. `internal/cli/tui/model.go::applyEvent` 的 switch 里**没有 `plan_update` 分支** —— 就算帧发出去了，TUI 也不认。

两端单测**全绿**，且它们的绿是货真价实的。A 打不到（掏空任一端，那一端会红，证明测试有效 —— 链路依然是断的）；H 打不到（`plan_update` 不是幻影名，帧类型真实存在、构造函数真实存在）。这个事实早就被记在 `docs/superpowers/acceptance-breakdown.md` 的 A2/G05 条目里，但在本条落地之前，**没有任何一条评审手法会主动去找它** —— 它只能靠有人恰好读到那一段。J 就是为了把「恰好读到」换成「每轮必扫」。

## K. 删除面：本轮删掉的每一条防线

**做什么**：对本轮 diff 里每一处**删除**（测试、断言、表行、正则分支、散文防线），问它删掉的是哪一条防线，并造一次变异证明**剩下的防线仍然在**。

### K 为什么不是 A、B、D、G 的重复

- **A（变异测试）** 掏空的是**被测函数**，问「测试会不会红」—— 它预设那条测试还在。本轮被删掉的测试，A 根本不会去跑它。
- **B（门禁探针）** 造探针问「门禁拦不拦得住」—— 它预设被查的那道防线存在。
- **D（空壳测试识别）** 读的是**留下来**的测试，问「它的绿是不是假的」。删掉的那条不在它的视野里。
- **G（接线激活）** 只看「本轮**接活**了什么」，方向正好相反。

四条手法**全部预设被查对象存在**。没有一条负责问「本轮少了什么」—— 而收窄一个正则、删掉一行表、删掉一条断言，在 diff 里长得和整理代码一模一样。

**本轮它就直接承重**：第 23 轮的修复把一个英文名词模式从「连字符或空格都认」收窄成「只认连字符」。这个收窄本身是对的（空格变体匹配的是动词短语，会在无关句子上误伤），但「收窄会不会让某个历史文档豁免表条目变成**死条目**（那张表的死条目判失败）、会不会丢掉某个活文档里的真实召回」全靠评审者临时想到去查 —— 没有任何一条手法要求他查。

### 怎么做

```sh
# 本轮删掉了多少条测试函数 / 断言？非零就逐条判「替换还是净删」
git diff <base>..HEAD -- '*_test.go' | grep -cE '^-(func Test|\s*(t\.(Error|Fatal)|require\.|assert\.))'

# 删掉的具体是哪些，带上下文读一遍
git diff <base>..HEAD -- '*_test.go' | grep -E '^-(func Test|\s*(t\.(Error|Fatal)|require\.|assert\.))'

# 非测试文件里删掉的正则分支 / 表行 / 常量 / 豁免项
git diff <base>..HEAD -- '*.go' ':!*_test.go' | grep -E '^-' | grep -v '^---'
```

**逐条判两件事**：

1. **替换还是净删**？同一个 diff 里有没有一条新增在承担它的职责？（改名、抽公共函数、多行合并成一张表都算替换 —— 但要求你**指出接替者**，不是感觉上有。）
2. **净删的那些，防线还在吗**？造一次变异：把被删断言原本会抓住的那个东西**放回代码里**，跑全套测试，确认仍有别的东西变红。**不红就是净删了一条唯一防线**，按阻塞记。

对**收窄**（正则、allowlist、扫描面、豁免表）额外问一次：被收窄掉的那部分**当前有没有活文件命中**？只有实测无命中才叫安全收窄，而这必须跑一遍现有内容 —— 读代码读不出来。

### 什么输出算发现问题

- 净删了一条断言 / 测试 / 表行，且指不出接替者 → **阻塞**。
- 收窄了一道模式，且没有实测收窄掉的那部分当前零命中 → **阻塞**。
- 删掉的是**豁免表条目**，而那张表带死条目检测 → 至少要说明为什么它不再需要（这是本仓唯一「只能删不能加」的合法方向，但仍要写理由）。
- 一段**散文防线**被换成了会跑的表 → 这是好事，但必须逐句核对「表覆盖了散文声称的每一件事」，这正是本条要问的那个问题。

**真实实例（本仓，第 24 轮）**：上面那次正则收窄之外，同一个 commit 还删掉了整段描述覆盖面的散文、换成了一张会执行的用例表 —— 方向完全正确。但没人核对「表是否覆盖了散文声称的每一件事」，于是表里少了两行（产品名与名词零宽相接的 CamelCase 标识符，单复数各一），而那两行恰恰是唯一能钉住「某个正则组必须非空」这个设计选择的用例。结果是：散文里那条设计选择的因果**写反了**，表里又没有用例能拆穿它，一条假机制断言就这样裸奔了整整一轮。

## 一轮评审的执行顺序

顺序有依赖，不要打乱：

1. **C（测试名核对）** —— 先做，否则 A、B 的结论全是假阳性。
2. **E（不会被执行的测试）** —— 排除掉根本没跑的测试，缩小 A 的范围。
3. **A（变异测试）** —— 对剩下的证据测试逐条掏空。
4. **D（空壳测试识别）** —— A 没抓到的，用读代码补。
5. **B（门禁探针，正反两向）** —— 对每道门禁。
6. **G（接线激活的路径）** —— 对本轮的接线改动。
7. **K（删除面）** —— 对本轮的删除改动，**必须排在 A、B、D 之后**：K 问的是「剩下的防线还在吗」，而「剩下的防线是不是有效的」得先由 A/B/D 判完，否则 K 会拿一条空壳测试当作接替者放行。G 与 K 是同一份 diff 的两个方向（接活了什么 / 少了什么），挨着跑最省事。
8. **H（幻影名）+ F（文档虚报）** —— 全仓扫。
9. **J（两端契约的连通性）** —— 全仓扫，**必须排在 H 之后**：H 先确认名字真实存在，J 才问「存在的这个名字两端接上了没有」。顺序反过来会把幻影名误诊成死契约，而两者的修法相反 —— 幻影名要删掉，死契约要接上。
10. **I（竞态与资源）** —— 收尾。

跑完记得：`git status` 确认探针和掏空的改动都已恢复，工作树干净。

📌 **文档里的章节顺序是字母序，与执行顺序无关**（A–I 一直如此：执行从 C 起、A 排第三）。所以 J、K 写在 I 之后是排版位置，它们在执行顺序里的位置分别是上面的第 9 步与第 7 步。

📌 **`0-bis`（实施纪律）不在这个顺序里**，因为它不是评审步骤 —— 它约束写代码的人。评审侧对它的检查已经并进第 8 步（F4）。

## 「干净」的定义

**一轮干净 = 完整跑完 A–K 十一条，零阻塞。**

不是「没发现问题」，是「按这十一条找过，没找到」。少跑一条就不算这一轮，不能计入「连续三轮」。

⚠️ **新手法落地的那一轮本身不能计入连续计数** —— 按「怎么用」第二条，新手法从**下一轮**开始生效。据此：

| 轮次 | 判据 |
|---|---|
| 第 22 轮（J 落地） | A–I 九条 |
| 第 23 轮 | A–J 十条 |
| 第 24 轮（K 落地） | A–J 十条 |
| 第 25 轮起 | A–K 十一条 |
